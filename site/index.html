The IDE · for developers

Your repo, in a sandbox, with a team of agents

Open a repository from GitHub, plan changes, let agents you configured carry them out under guardrails, and push the result back.

  1. 01

    Sync GitHub

    One button connects your account and lists every repo you can reach, private and organisation ones included. Open one and the whole history is cloned into a fresh sandbox. The token is encrypted on the server and never sent to the browser.

  2. 02

    Detected, then approved

    The repo is scanned for services, stacks, ports and start commands. You see the plan before anything runs, and can change any command.

  3. 03

    A real IDE, a real preview

    Monaco editor, a shell inside the container, logs and a live preview on its own isolated origin. Every save is written through the container, so hot reload never misses a change.

  4. 04

    Plan first, then build

    In Planning mode the agent researches your code and writes an Implementation Plan and a Task List. Comment on any line like a shared document, ask for a revision, or press Proceed.

  5. 05

    Built task by task, then explained

    Tasks tick off as they finish, checks run in the sandbox once you approve them, and a Walkthrough sums up what changed, what was verified and what is left for you.

  6. 06

    Your coding agents, as a team

    The Agents panel manages the team that lives in your repo, in the OpenGAP / GitAgent layout. Each agent is a folder: SOUL.md says who it is, which files it owns and who it hands work to, and RULES.md says what it must and must not do. Set one up in a click, edit it in a form, and smoke-test it against your model.

  7. 07

    Watch the agents' workflow

    A task is routed by name, by the files an agent owns, or by a classifier with a confidence floor. Each agent gets its attempts, then hands off with a compact brief instead of a transcript, and a terminal agent stops and asks you. The Workflow view lights up live while it happens.

  8. 08

    Guardrails enforced in code

    Guards in hooks/ run on the exact content an agent is about to write, and on commands. Four are sealed in code and cannot be switched off: secret scanning, protected reads, no force push and no sudo. The rest you can toggle, add and scope to agents.

  9. 09

    A record you can trust

    Every run keeps a shared record of the work. What the system saw happen is marked verified; what a model only said is marked claimed. Failed approaches can't be erased, so no agent repeats a dead end.

  10. 10

    Source Control and Git Graph

    See every change from you and the agents, commit and push, push to a new branch and open a pull request, or publish a project as a new repo. The Git Graph shows every branch's history with refs, commit details and per-file diffs.

Model-agnostic by design

Your model. Your key. Your code. I provide the infrastructure.

This follows the intent behind Lyzr's model-agnostic framework: the platform should never decide where your work is sent or who owns the result.

Your model

Groq, OpenAI, Anthropic or Gemini, chosen per message in the IDE, per agent in agent.yaml, or per workflow in Agent Hub. An agent pulled from the internet is never allowed to choose its own model, because that would decide where your code goes.

Your key

Paste any key and its provider is recognised from its shape and checked once. Several keys per provider are pooled and routed by their live rate limits. Keys are stored on the server, never shown again in full, and never sent to a browser.

Your ownership

Everything you build is pushed to your own GitHub as a normal repository with a README. Agents and guardrails are plain files in your repo. Nothing ties the code to Jr Architect, and the app keeps running without it.

How a sandbox starts

  1. The repo is cloned with your GitHub access, or uploaded from your computer.
  2. Files like package.json, go.mod, manage.py or Cargo.toml decide the stack, port and commands.
  3. You approve the plan. Missing images are built once and reused.
  4. The container starts with 1 CPU, 1 GB of memory and a 100 process limit. Only the workspace is mounted.
  5. The app gets a preview address on its own host, so it can never read the IDE's session.

Kept fast and tidy

  • Dependency installs skip audit and funding round trips and reuse a shared cache.
  • Build-mode apps share one prepared node_modules volume, so they start in seconds.
  • Idle sandboxes stop after 15 minutes. Saved projects stay.
  • Every container is labelled with the server that started it, so one server never removes another's work.

Technical architecture

How it fits together

One Go binary serves the UI, owns the sandboxes and proxies everything else. A Node agent service runs the agents and the OpenGAP team. Both keep their records in MongoDB. Generated apps call their workflows over webhooks.

Sandboxes

One container per project from a stack image, with --memory 1g --cpus 1 --pids-limit 100. Only /workspace is mounted, and idle sandboxes expire.

Agent harness

Agents are versioned definitions with input and output schemas. Input is validated and coerced, tools are limited per agent, and a wrong-shaped answer is retried with a correction.

OpenGAP team

Agents from .gitagent/agents/ are routed by name, owned files or a classifier, get attempts, hand off with a compiled brief and stop at a terminal agent.

Guardrails

Edit and command guards from hooks/ run on the real content. Four are sealed in code; a broken guard file stops a run instead of weakening it.

Proxy

A host-based reverse proxy sends p-<token> hosts to each sandbox. The agent service is reached only through /agent/* on loopback.

GitHub

Commit, status and history run in the sandbox without any credentials. Fetch and push run in a separate, short-lived git container that never runs repository code, so the token is never where your repo's code could read it. It is encrypted at rest.

Database

MongoDB holds users, sign-ins, projects, agents and their versions, workflows, runs, agent memory, API keys and playground chats, each with its own id. Secrets are encrypted before they are stored; API keys are kept only as hashes.

Deployment

One Go binary with the UI and templates embedded, the Node service beside it, and Docker on the host. Any Linux machine with root can run it.

Scaling

Durable state lives in MongoDB rather than on one machine's disk, so more servers and Docker hosts can share it. Per-user model limits keep one person from slowing everyone.

Production notes

Built to treat every repo, prompt and browser as untrusted

An app builder runs code it did not write. So I audited Jr Architect the way an attacker would look at it, wrote down every weakness with a severity, and fixed the most serious ones first.

A written security audit

Every part of the system was mapped: who can call what, what each piece trusts, and what a hostile repository, a manipulated browser or a misled AI model could reach. Each weakness is ranked from critical to low, with the fix order.

Your GitHub token stays out of reach

The most serious finding: during a push, a hostile repository could read the token. Now fetch and push happen in a separate container that runs no repository code, and a test plants every known trick (hooks, filters, proxies, helpers) to prove nothing sees it.

The AI proposes, the server decides

When the coding agent wants to run a command, a server-side policy decides. Touching git internals, secrets or the container engine is refused. Network access, installs and deletes wait for your approval. Ordinary work like tests and builds just runs.

The browser is not trusted

Who you are comes from your sign-in, never from what the page sends. Every request for a sandbox, file, agent or workflow is checked against its owner on the server, so changing an id in a request gets you nothing.

Files stay inside the project

Every file read and write goes through a guarded root that refuses ../ paths and symlinks pointing out of the project, so a repository cannot trick the server into touching anything else.

Isolated sandboxes

Each project runs in its own container with CPU, memory and process limits, no extra privileges and no access to the container engine. The public deployment adds rootless containers, a firewall and a fixed disk quota.

Secrets never reach the page

Provider keys, GitHub tokens and OAuth secrets live only on the server, encrypted at rest, and are redacted from any error message that could reach you.

Tested, including the attacks

Over 170 automated tests, including negative ones: another user's ids, path escapes, planted git traps and refused agent commands. The agent and workflow tests run both with MongoDB and without it.

Inspired by architect.new

What I picked from architect.new, and how it fits Jr Architect

architect.new showed what an AI app builder should feel like. I took the ideas that matter most to someone who doesn't code and built them on the same foundations: a Go core and a MongoDB database, so the two think about apps, agents and data in the same way.

Go at the core

Like architect.new, the server is written in Go: one fast binary that serves the app, runs the sandboxes and handles every request.

MongoDB for the data

Like architect.new, the data lives in MongoDB. Users, projects, agents, workflows and runs are documents, each with its own id, and agents and workflows keep every saved version.

Agents as first-class records

An agent is stored as a versioned definition with its instructions, tools, input and output schemas and guardrails, ready to run on its own or inside a workflow, as in Lyzr's agent model.

Secrets on the server

Model keys and GitHub access stay server-side and encrypted, so the app you build and the page you use never hold them.

A consultant before code

architect.new starts by asking about your idea. Jr Architect does the same with a short interview of design decisions, each with a recommended answer, so a vague prompt still becomes a precise app.

Plan, then agents, then app

The same three phases: an editable spec first, then the AI agents and workflows, then the app. Here each phase is visible in one window, and the plan can be changed before anything is built.

Agents built with the app

architect.new builds agents in Lyzr Studio alongside the app. Jr Architect builds them in Agent Hub and wires the app to them through webhooks, so the agents stay usable on their own afterwards.

Model-agnostic from the start

Lyzr's framework lets you choose the model. Jr Architect keeps that promise everywhere: per message, per agent and per workflow, with your own keys.

Your code on GitHub

architect.new connects to GitHub. Jr Architect syncs both ways: open any repo, and push every built app to your account with a README.

Compatible with Lyzr apps

An app exported from Lyzr, recognised by its workflow.json or response_schemas/, is detected and runs in a Jr Architect sandbox as a Next.js app, so you can keep working on it in the IDE.
